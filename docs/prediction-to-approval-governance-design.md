# Prediction-to-Approval Governance Design

**Milestone:** 59A — Prediction-to-Approval Governance Design
**Status:** Design Complete
**Date:** 2026-05-30
**Author:** SentinelFlow Engineering

---

## 1. Purpose

This document defines the architecture, data flow, operator actions, and safety boundaries for integrating the Prediction Engine (Milestone 55–58) with the Guardian Gate approval workflow (Milestone 43).

The goal is to allow operators to elevate a machine-generated prediction into a governed, human-controlled approval event — without granting the Prediction Engine any autonomous execution capability.

**Core principle:**
> A prediction can only request governance review.
> It cannot approve, reject, or execute anything on its own.
> Every action that follows a prediction requires explicit human approval.

## 2. Current Prediction Card Behavior

| Property | Current State |
|---|---|
| **Generated by** | `SentinelPredictionEngine.processSignals()` |
| **Persisted to** | `Sentinel_Prediction__c` (Score ≥ 40%) |
| **Status values** | `Critical` (≥70%), `Warning` (40–69%) |
| **Operator fields** | `Operator_Decision__c` (Pending / Confirmed / Dismissed / False Positive / Useful) |
| **Dashboard widget** | Prediction card in `zentomDashboard` LWC |
| **Approval linkage** | ❌ None — not yet connected to Guardian Gate |
| **Execution capability** | ❌ None — prediction cannot trigger any action |

---

## 3. Governance Integration Objective

Connect prediction cards to the Guardian Gate approval and Action Center execution workflow so that:

1. An operator reviewing a prediction card can **request a governed approval** from within the dashboard.
2. The request appears in the **Guardian Gate approval queue** as a `Sentinel_Incident__c` or a linked `Zentom_Policy_Decision__c`.
3. An approver (human) reviews and **approves or rejects** the request.
4. If approved, the **Action Center** handles execution — not the Prediction Engine.
5. Every step is recorded in `Sentinel_Audit_Log__c`.

## 5. Operator Actions

The prediction card LWC will expose the following operator actions via button controls:

| Button | Action | Outcome |
|---|---|---|
| **Review Prediction** | Open full prediction detail modal | Displays score, explanation, signal breakdown |
| **Request Approval** | Calls `SentinelPredictionGovernanceService.createApprovalFromPrediction()` | Creates `Sentinel_Incident__c` in Guardian Gate queue |
| **Dismiss** | Sets `Operator_Decision__c = 'Dismissed'` | Marks prediction as reviewed and dismissed; no approval created |
| **Mark Useful** | Sets `Operator_Decision__c = 'Useful'` | Positive trust signal; increments `Operator_Trust_Score__c` |
| **Mark Noisy** | Sets `Operator_Decision__c = 'False Positive'` | Negative trust signal; decrements `Operator_Trust_Score__c` |

### Rules
- **Request Approval** is only available when `Operator_Decision__c = 'Pending'`.
- **Dismiss**, **Mark Useful**, **Mark Noisy** are mutually exclusive and terminal — once set they cannot be undone from the UI.
- A dismissed prediction **cannot** have an approval created after dismissal.
- All button actions write to `Sentinel_Audit_Log__c`.

## 6. Approval Record Mapping

When **Request Approval** is clicked, `SentinelPredictionGovernanceService` creates:

### `Sentinel_Incident__c`

| Field | Value |
|---|---|
| `Name` | `PRED-{Prediction_Score}-{Source}-{Timestamp}` |
| `Type__c` | `Predicted Anomaly` |
| `Risk_Level__c` | Mapped from `Sentinel_Prediction__c.Status__c` (Critical / Warning) |
| `AI_Confidence__c` | `Sentinel_Prediction__c.Confidence_Score__c` |
| `AI_Reasoning_Status__c` | `Prediction-Triggered` |
| `Approval_Status__c` | `Pending` |
| `Source_Prediction__c` | Lookup to `Sentinel_Prediction__c.Id` *(new field — 59B)* |
| `Environment__c` | Derived from `Event_Source__c` |
| `Description__c` | `Sentinel_Prediction__c.Explanation__c` |

### `Sentinel_Audit_Log__c` (on Request Approval)

| Field | Value |
|---|---|
| `Action__c` | `Prediction Approval Requested` |
| `Actor__c` | Running user |
| `Record_Id__c` | `Sentinel_Prediction__c.Id` |
| `Details__c` | Score, source, timestamp |

## 7. Policy Decision Mapping

When the Guardian Gate approver clicks **Approve** or **Reject**:

### `Zentom_Policy_Decision__c`

| Field | Approve | Reject |
|---|---|---|
| `Decision__c` | `Approved` | `Rejected` |
| `Incident__c` | Linked `Sentinel_Incident__c.Id` | Linked `Sentinel_Incident__c.Id` |
| `Rationale__c` | Approver notes (optional) | Approver rejection reason |
| `Decided_By__c` | Running user | Running user |
| `Decision_Date__c` | DateTime.now() | DateTime.now() |

### Feedback back to Prediction

After decision, `Sentinel_Prediction__c.Operator_Decision__c` is updated:
- **Approved** → `Confirmed`
- **Rejected** → `Dismissed`

This feeds into the trust score model (`Operator_Trust_Score__c`) per the rules defined in Milestone 56C.

## 8. Audit Log Requirements

Every state transition in the prediction-to-approval lifecycle must produce a `Sentinel_Audit_Log__c` record:

| Event | Action Field Value |
|---|---|
| Prediction generated | `Prediction Generated` |
| Operator clicks Request Approval | `Prediction Approval Requested` |
| Guardian Gate approves | `Prediction Approval Confirmed` |
| Guardian Gate rejects | `Prediction Approval Rejected` |
| Operator dismisses | `Prediction Dismissed` |
| Operator marks useful | `Prediction Marked Useful` |
| Operator marks noisy | `Prediction Marked False Positive` |

All audit records must include: `Actor__c`, `Record_Id__c`, `Details__c`, `CreatedDate`.

## 9. Safety Boundaries

These boundaries are **non-negotiable** and must be enforced at the Apex service layer — never bypassed by UI or automation:

| Boundary | Rule |
|---|---|
| **No autonomous execution** | `SentinelPredictionGovernanceService` can only create approval records. It cannot execute, approve, or trigger remediation. |
| **No self-approval** | The user who created the approval request cannot be the same user who approves it (enforce via Guardian Gate existing logic). |
| **No prediction chain** | A prediction cannot spawn another prediction. Approvals cannot trigger new predictions. |
| **No bypass on Critical** | Even a Critical (≥70%) prediction requires the same human approval process. Severity does not grant automatic execution. |
| **Dismissed is terminal** | A dismissed prediction cannot have Request Approval invoked. Enforced in Apex before DML. |
| **Trust score is advisory** | `Operator_Trust_Score__c` informs weight calibration only. It does not auto-approve or auto-dismiss. |
